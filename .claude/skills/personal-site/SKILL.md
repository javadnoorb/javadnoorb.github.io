# Personal site maintenance

This repo builds a static personal website + auto-generated PDF resume for
Javad Noorbakhsh, deployed to **https://javadnoorb.github.io/** via GitHub
Pages. It is NOT a Jekyll site (there's a `.nojekyll` marker) - it's plain
Python + Jinja2, chosen so the whole pipeline (fetch publications, render
HTML, generate PDF) is one language.

## Architecture

```
data/profile.yaml        - hand-edited: bio, education, experience, skills,
                            social links, research_focus. Source of truth
                            for everything except publications. The bio's
                            "{years}" placeholder is filled at build time
                            (`load_data`) from `career_start_year`, so the
                            "N years of experience" never goes stale -
                            don't hardcode the number.
data/publications.json   - auto-generated by scripts/fetch_publications.py.
                            Never hand-edit; fixes belong in the fetch
                            script (see "Known gotchas" below) so they
                            survive the next scheduled re-fetch.
templates/*.html          - Jinja2 templates: base, index, research
                            (Research Highlights), projects, publications,
                            resume, resume_pdf.
data/scholar_stats.json  - auto-generated citation totals / h-index,
                            shown on home + publications pages if present.
static/                   - CSS + images, copied as-is into _site/.
scripts/fetch_publications.py - pulls + cleans Google Scholar publications.
scripts/build.py          - renders templates + data into _site/: pages,
                            404.html, PDF resume (WeasyPrint),
                            publications.bib, sitemap.xml, robots.txt and
                            the og-profile.png social preview image.
scripts/dev_server.py     - local preview server for _site/. Use this
                            instead of `python -m http.server` - see
                            "Local workflow" below for why.
_site/                     - build OUTPUT, gitignored. Never committed;
                            CI uploads it straight to GitHub Pages
                            (Pages source = "GitHub Actions").
tests/                     - pytest suite (helpers + render smoke test).
                            Run `python -m pytest` before pushing.
.github/workflows/build.yml - PRs: tests + full build. master pushes,
                            weekly (Mon 06:00 UTC) and manual runs: also
                            fetch publications, commit data/*.json back to
                            master with "[skip ci]", and deploy _site/.
```

## Local workflow

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt    # requirements.txt + pytest
python scripts/fetch_publications.py   # refreshes data/publications.json
python scripts/build.py                # renders _site/
python -m pytest                       # tests
python scripts/dev_server.py 8000      # preview, with caching disabled
```

**Use `scripts/dev_server.py`, not plain `python -m http.server`.** The
latter sends no `Cache-Control` header at all, and the user's phone browser
(Android Chrome) was observed caching pages/images well past what's
reasonable, requiring a private window to see rebuilds. `dev_server.py`
sends `Cache-Control: no-store` on every response, which fixed it - but
only for requests made *after* it started serving. If the user reports
still seeing stale content even with this server running, their browser
already has old entries cached from before (from a plain `http.server` in
an earlier session, most likely) - the fix there is to restart on a new
port (browser cache is keyed by origin including port), not to fight the
existing cache. Also note: **background processes from an earlier turn are
invisible to `ps`/`pkill` in a fresh Bash tool call** even though they're
still running and reachable - if you need to replace a running dev server,
just start the new one on a different port rather than trying to kill the
old one.

WeasyPrint needs system libs: `libpango-1.0-0 libpangocairo-1.0-0
libgdk-pixbuf2.0-0 libffi-dev shared-mime-info` (apt). They were present in
the cloud sessions used so far; a fresh venv plus `requirements-dev.txt` was
enough to build and run the tests there. If the PDF step fails to import
WeasyPrint, install these first.

**User's review habit**: they preview before anything goes live - over
Tailscale from their phone in local sessions (rediscover the IP with
`tailscale ip`; it's machine-specific), or in Claude Code cloud sessions
from a rendered PDF/screenshot or the diff itself. Push work to the
session's feature branch first and wait for the go-ahead ("merge it to
master"; they also say "main" - the remote's default branch is `master`).
Then run the tests, `git fetch origin master`, merge it in if CI added a
data commit (it's a plain fast-forward if the branch already has it), and
`git push origin HEAD:master`. Always get an explicit go-ahead before
pushing to master - this user has consistently asked to review before push.

**Resume/profile edits are collaborative, one piece at a time.** Propose
the exact new text in chat and wait for the user's OK before editing, then
show the diff and wait again before moving to the next question. Ask one
focused question at a time rather than long lists. A Stop hook in cloud
sessions demands that uncommitted changes be committed and pushed to the
feature branch; that is fine (it's not master), so do it, and say so.

## Deploying

The remote is `javadnoorb/javadnoorb.github.io`, default branch **master**.
Local checkouts differ: some have a local `main` (push with `git push
origin main:master`), cloud sessions have `master` plus a `ccr-...` feature
branch (push with `git push origin HEAD:master`). Pushing to master
triggers the workflow, which builds and deploys - there is nothing to
rebuild or commit locally. The only thing CI commits back is `data/*.json`
(refreshed publications), so a rejected push just needs:


Dependencies are pinned exactly in `requirements.txt` (the PDF layout was
tuned against WeasyPrint 70.0). Bump deliberately and re-check the PDF.

Cloud sessions' network policy blocks `javadnoorb.github.io` itself, so
the live site can't be fetched to verify a deploy. Check the "Build and
Deploy Site" Actions run for the pushed commit instead (build + deploy
jobs), and if needed rebuild that exact commit locally and inspect
`_site/`.

## Cache-busting on the live site

GitHub Pages doesn't allow custom cache headers (fixed at `max-age=600`
with an ETag) and that's a reasonable policy on its own, but Android
Chrome has repeatedly been observed serving stale assets (images, the PDF)
well past that window regardless. The fix, already in place: every static
asset reference in templates goes through `asset_version()` (a Jinja
global registered in `build.py`), which appends `?v=<content-hash>`.

**This is a per-file content hash, not a build timestamp** - an earlier
version used `time.time()` at build time, which busted every asset's URL
on every single rebuild even when the file hadn't changed, defeating
caching entirely on a site meant to run long-term. Content hashing means
an unchanged file keeps the same URL forever (stays cacheable) while a
changed one always gets a fresh URL (no staleness possible, regardless of
browser quirks). `resume.pdf` is a special case: it's hashed by its
*source inputs* (`profile.yaml`, `publications.json`, `resume_pdf.html`,
and `scripts/build.py`, whose display filters shape the PDF's text),
not its own output bytes, because WeasyPrint embeds a creation timestamp
that would otherwise change the hash on every build regardless of visible
content. If you add a new static asset reference in a template, route it
through `asset_version()` too rather than a bare path.

## Known gotchas

- **`scholarly` can hang indefinitely in CI**, not just fail - observed a
  12+ minute hang with no output when Google Scholar soft-blocks a
  GitHub-hosted runner IP. The workflow already has `timeout-minutes: 4` +
  `continue-on-error: true` on that step so a hang can't block the
  build/deploy steps. A `SERPAPI_KEY` repo secret would make fetches more
  reliable but the user has deliberately deferred getting one (needs phone
  verification with SerpApi) - don't push to add it unprompted.
- **`bibtexparser` must stay pinned `<2`** - `scholarly` 1.7.x imports
  `bibtexparser.bibdatabase`, removed in bibtexparser 2.x.
- **Jinja gotcha**: never name a dict key `items` when you plan to access it
  as `thing.items` in a template - dict.items() (the method) shadows it.
  This is why `profile.yaml`'s skills groups use the key `skills:` inside
  each category, not `items:`.
- `fetch_publications.py` already handles: truncating long author lists to
  5 + "et al." (but keeps the site owner's own name visible even if their
  position would otherwise be truncated away), dropping Scholar's
  mis-scraped "author list as title" garbage entries, de-duplicating a
  paper that got scraped multiple times as preprint+journal+abstract
  (keeps the published version over a preprint, carrying the group's
  highest citation count), dropping zero-citation entries
  (usually stray conference posters), dropping conference abstracts
  (`is_poster`: venue says "abstract", title starts with "Abstract" or
  ends in a poster number, or the link has `_Supplement/` - AACR prints
  meeting abstracts as Supplement issues of *Cancer Research* /
  *Clinical Cancer Research*, so the venue alone looks like a real
  journal paper; five slipped through that way before), and a small `VENUE_OVERRIDES` list
  patching a handful of publications where Scholar's scrape drops the
  venue entirely (cross-checked against the user's resume PDF). Extend
  that list rather than hand-editing `publications.json` if you find more
  missing venues.
- The fetch refuses to overwrite `publications.json` when it keeps under
  70% of the papers already there (a partial scrape); override with
  `FORCE_PUBLICATIONS_UPDATE=1` only when papers were genuinely removed.
  DOIs come from the link when it contains one (`build.doi_from_link`),
  else from a previous run, else a best-effort Crossref title lookup.
- Author-role badges ("First author" / "Senior author") are derived in
  `build.author_role` and deliberately only trust position 1 or the last
  slot of an *untruncated* list - the truncation step may swap the owner
  into the last visible slot of a long list. `build.author_position`
  applies the same rule to any position (the last visible slot of a
  truncated list returns None); the Resume tab's "Selected Publications"
  uses it to show every paper where the user is **1st or 2nd author**
  (the user's explicit choice - all of them, no count cap), with a link
  to the full list.
- **Patents are not papers.** Scholar mixes them in; `build.split_patents`
  pulls out anything linking to Google Patents, and both the PDF and the
  Publications page show them in a small, unnumbered "Patent(s)" section
  after the papers (number derived from the link, e.g. "U.S. Patent
  Application US 2025/0378559 A1"). The user asked for it to be separate
  but low-key - there's only one, so don't give it prominence. Patents
  are also excluded from highlights, the Resume tab and publications.bib.
- **Scholar's raw strings are normalized only at display time**
  (`format_authors`, `format_venue` filters in `build.py`), not in
  `publications.json`: author lists come in two shapes ("A and B and C"
  vs "A, B, et al.") and occasionally carry degree prefixes ("PhD
  Javad..."); venues are inconsistently cased ("Nature communications",
  "BioRxiv"). Use these filters in any new template that shows
  publications, on both the site and the PDF. On the site, prefer the
  `pub_meta` macro in `_macros.html` ("Authors · Venue · Year"), which
  skips blank parts so a venue-less paper gets no dangling "·".
  `tests/test_build.py` also builds the whole site and fails on any
  relative link/asset that doesn't exist in `_site/`.
- `scripts/build.py`'s `get_highlighted()` picks the homepage's
  "Highlighted Publications" by citation count (impact), not recency -
  intentional, because a pure recency sort was burying the two flagship
  *Nature* papers behind low-citation recent preprints.
- **The nav bar has no built-in margin for growth.** It already overflowed
  the viewport on phones once (6 items: Home, Research, Projects,
  Publications, Resume, Download CV), forcing horizontal scroll, before
  `.site-header nav` got `flex-wrap` plus a `max-width: 480px` media query
  that centers it and tightens spacing. If you add another nav item, check
  phone width (~400px) again rather than assuming the existing wrap rules
  scale indefinitely.

## Research Highlights page (research.html)

A gallery of ~13 flagship papers, each with a figure actually extracted
from the source PDF (via `pdftoppm -r 300` + PIL crop, never a stock/
placeholder image) and a plain-English summary grounded in actually
reading the paper - never written from the title/metadata alone. Ordered
in two tiers, each tier newest-first internally: first-author papers
come first, then papers where the user is 2nd/3rd/4th author, and within
that second tier it's sub-grouped by author position (all 2nd-author
papers before all 3rd-author, before all 4th-author). Re-derive author
position from `data/publications.json`'s `authors` field (comma-separated,
truncated-with-"et al." list) when reordering - don't guess from memory.
Full methodology, per-paper key findings, and exact crop coordinates are
logged in
`~/research-papers/notes.md` (outside this repo, alongside the downloaded
source PDFs; only exists on the user's own machine, not in cloud
sessions) - see the `research-theme-sync` skill for the general method
and check that notes file before re-reading a paper from scratch.

Only first-author (or, per the user's later broadened call, 2nd/3rd/4th-
genuine-position - never a truncation-swapped-in position) papers belong
here; a paper already covered here that the user was a middle/large-
consortium author on doesn't get double-counted elsewhere. When cropping
a figure, always re-check against the *actual* page render for content
right at the edges (axis tick labels, legend edges, a second row of
subpanels) - several early crops were a little too tight and clipped real

  amounts) in resume bullets. Several bullets are deliberately left
  qualitative because the user wants to supply real numbers themselves -
  ask, don't invent.
