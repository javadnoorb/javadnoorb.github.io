# Personal Site

Source for [javadnoorb.github.io](https://javadnoorb.github.io/): a small
static site with a home page, research highlights, side projects, a
publications page kept in sync with Google Scholar, and a resume page that's
also exported as a downloadable PDF. A GitHub Actions workflow re-fetches
publications, rebuilds everything and deploys it to GitHub Pages on a
schedule, so it stays current without manual work.

## How it fits together

- `data/profile.yaml` — bio, education, experience, skills, links, research
  highlights, projects. Edit by hand.
- `data/publications.json` — publication list. Generated by
  `scripts/fetch_publications.py`; don't edit by hand (fixes belong in the
  fetch script so they survive the next re-fetch).
- `data/scholar_stats.json` — total citations / h-index / i10-index, also
  written by the fetch script. Shown only when present.
- `templates/` — Jinja2 templates for the site pages, the 404 page and the
  PDF resume. Shared snippets live in `templates/_macros.html`.
- `static/` — CSS and images, copied as-is into the built site.
- `scripts/fetch_publications.py` — pulls publications from Google Scholar,
  cleans them up (duplicates, posters, garbled entries) and fills in DOIs.
- `scripts/build.py` — renders everything into `_site/`: the HTML pages,
  `resume.pdf`, `publications.bib`, `sitemap.xml`, `robots.txt` and a social
  preview image. `_site/` is build output and is not committed.
- `tests/` — pytest tests for the data-cleaning and formatting helpers, plus
  a smoke test that renders every page.
- `.github/workflows/build.yml` — on pull requests, runs the tests and a full
  build. On pushes to `master`, weekly, and on demand, it also re-fetches
  publications, commits any data change back to `master`, and deploys
  `_site/` to GitHub Pages.

## Local development

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
```

WeasyPrint (used for the PDF) needs system libraries. On Debian/Ubuntu:

```bash
sudo apt-get install libpango-1.0-0 libpangocairo-1.0-0 libgdk-pixbuf2.0-0 libffi-dev shared-mime-info
```

On macOS: `brew install pango`.

```bash
python scripts/fetch_publications.py   # optional: refresh data/publications.json
python scripts/build.py                # writes _site/
python scripts/dev_server.py 8000      # preview at http://localhost:8000
python -m pytest                       # run the tests
```

`dev_server.py` sends `Cache-Control: no-store`, so phone browsers don't
keep showing an old build.

Dependencies are pinned exactly in `requirements.txt` so an upstream release
can't silently shift the PDF layout. When bumping one, rebuild and look at
`_site/resume.pdf` before merging.

## Deployment setup

1. **GitHub Pages source**: Settings → Pages → Build and deployment → Source:
   **GitHub Actions**. The workflow uploads `_site/` directly; nothing is
   served from a branch folder.
2. **(Recommended) SerpApi key** so scheduled fetches in CI actually succeed.
   Google Scholar aggressively blocks scraping from datacenter IPs (including
   GitHub Actions runners), so the `scholarly` fallback is often blocked
   there even though it works fine locally. Get a key at
   https://serpapi.com/ and add it as a repo secret named `SERPAPI_KEY`
   (Settings → Secrets and variables → Actions).

## Safety nets

- If a fetch fails or is blocked, `data/publications.json` is left untouched.
- If a fetch returns far fewer papers than are already on the site (under
  70%), it's treated as a partial scrape and also ignored. Run with
  `FORCE_PUBLICATIONS_UPDATE=1` to accept a genuinely smaller list.
- DOI lookups on Crossref are best-effort; a failed lookup just means no DOI
  link for that paper until a later run finds one.
- To change the update frequency, edit the `cron` schedule in
  `.github/workflows/build.yml`.
